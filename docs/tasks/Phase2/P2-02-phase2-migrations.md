# P2-02 — Phase 2 models & migrations
Scope: backend
Depends on: P2-01
Skills: database, architecture, testing
PROJECT.md: §4b, §12, §13

## Objective
All remaining Phase 2 SQLAlchemy models and one Alembic migration creating them, with the
constraints the later cards rely on. No endpoints, no logic.

## Files
- `backend/app/features/categorization/models.py` — `categorization_runs`
- `backend/app/features/recurring/models.py` — `recurring_series`, `recurring_occurrences`
- `backend/app/features/goals/models.py` — `goals`, `goal_allocations`
- `backend/migrations/versions/*_add_phase2_tables.py`
- `backend/tests/test_phase2_models.py`

## Schema slice
Use `PROJECT.md` §4b **exactly** — UUID string PKs, UTC timestamps, money as signed integer
`*_minor`. Constraints that must exist:
- `recurring_series`: unique `(account_id, merchant_key)`; index on `(user_id, status)`.
- `recurring_occurrences`: **unique on `transaction_id`** (a transaction belongs to at most one
  series); index on `series_id`; FK to transactions with `ON DELETE CASCADE`.
- `goal_allocations`: index on `goal_id`; FK with `ON DELETE CASCADE`.
- `categorization_runs`: index on `(user_id, created_at)` for the history query.

## Steps
1. Define the five models in their owning feature folders (each folder gets `__init__.py`;
   routers/services arrive in later cards).
2. Ensure every new model is imported where Alembic's metadata is assembled — a model that no
   module imports is silently missing from the autogenerated migration.
3. Autogenerate, then **hand-verify** the migration: all constraints above present, types
   portable per the database skill (no SQLite-only types — Phase 4 targets Postgres),
   `down_revision` chains onto P2-01's migration.
4. Write a working `downgrade()` that drops the tables in FK-safe order.
5. Amount and date columns only — no derived/computed columns. `next_expected_date` is stored
   (the detector computes it); "missed charge" is **not** stored (§12: it stops being true the
   moment the charge lands).

## Acceptance
- `alembic upgrade head` builds all five tables on an empty DB; `downgrade` then `upgrade` again
  is clean.
- Unique `(account_id, merchant_key)` and unique `transaction_id` are enforced by the DB, not
  only by application code.
- All money columns integer; all PKs UUID strings; all timestamps UTC-aware.
- Deleting a transaction removes its occurrence row; deleting a goal removes its allocations.
- `ruff` + `ty` clean.

## Tests
- `test_phase2_models.py`: migration applies on a temp SQLite file; duplicate
  `(account_id, merchant_key)` rejected; a second occurrence for the same `transaction_id`
  rejected; cascade deletes verified for both cascading FKs.
