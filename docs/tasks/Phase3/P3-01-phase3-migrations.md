Scope: backend
Depends on: P2-02

## Objective
All Phase 3 SQLAlchemy models and one Alembic migration creating them, plus the single column
`user_settings` gains. No endpoints, no engines, no seed data.

## Schema slice
Use `PROJECT.md` §4c **exactly** — UUID string PKs, UTC timestamps, money as signed integer
`*_minor`, **every rate an integer `*_bps`**. Constraints that must exist:
- `mortgages`: `kind` text NOT NULL, one of `mortgage|works|consumer|auto` (the credit product the
  user recognises — a different axis from `repayment_type`, which is the maths; see §4c). Index on
  `(user_id, status)`; FK `property_id` → properties **nullable**, `ON DELETE
  SET NULL` (archiving a property must not delete the loan that financed it).
- `properties`: index on `(user_id, archived)`.
- `tax_profiles`: unique `(user_id, tax_year)`.
- `tax_brackets`: unique `(user_id, tax_year, kind, ordinal)`; index on `(tax_year, kind, ordinal)`
  for the system-row read.
- `tax_parameters`: unique `(user_id, tax_year, key)`; index on `(tax_year, key)`.
- Both parameter tables: `user_id` **nullable** FK → users, null = system row. Same convention as
  `categories` — do not invent a second one.
- `mortgage_simulations`: index on `(user_id, created_at)`.

## Steps
1. Define the six models in their owning feature folders (`__init__.py` each; routers and services
   arrive in later cards). `properties` and `tax` are new feature folders — follow the architecture
   skill's vertical-slice shape.
2. Add `declared_monthly_income_minor` (Integer, nullable) to `UserSettings`. No backfill: null is
   the meaningful default (§15 — derive from the ledger).
3. Ensure every new model is imported where Alembic's metadata is assembled — a model no module
   imports is silently absent from the autogenerated migration.
4. Autogenerate, then **hand-verify**: every constraint above present, no SQLite-only types
   (Phase 4 targets Postgres), `down_revision` chains onto the last Phase 2 revision.
5. Working `downgrade()`: drop in FK-safe order and drop the settings column.
6. **No derived columns.** No `outstanding_principal_minor`, no `monthly_payment_minor`, no stored
   estimate or simulation result — §4c retires `amortization_entries` and `projections` precisely
   so that these stay derived. A column here that a later card "fills in" is the bug this prevents.

## Acceptance
- `alembic upgrade head` builds all six tables plus the settings column on an empty DB;
  `downgrade` then `upgrade` again is clean.
- Unique `(user_id, tax_year)`, `(user_id, tax_year, key)` and `(user_id, tax_year, kind, ordinal)`
  are enforced by the DB, not only in application code.
- A NULL `user_id` row is accepted in `tax_brackets` and `tax_parameters` (system rows).
- Archiving or deleting a property leaves its mortgage row intact with `property_id` NULL.
- All money columns integer, all rate columns integer, all PKs UUID strings, timestamps UTC-aware.
- `mortgages.kind` exists, is NOT NULL and rejects a value outside the four.
- `ruff` + `ty` clean.

## Tests
- `test_phase3_models.py`: migration applies on a temp SQLite file; each unique constraint rejects
  its duplicate; NULL-`user_id` system rows insert; `ON DELETE SET NULL` verified on `property_id`;
  downgrade/upgrade round-trip.
